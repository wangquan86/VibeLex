**项目名称：** VibeLex  
**产品版本：** V1.0  
**文档修订：** 1.2  
**状态：** 设计规范

## 1. 架构目标

V1 面向“可审核的网络语言知识库”最小闭环：将人工或已授权数据集中的候选表达导入系统，完成清洗、归一化、去重、审核、发布、检索和追溯。

架构优先保证：

- 正式词条与未审核候选严格隔离；
- 数据来源、导入运行和词条证据可追溯；
- 已获授权的数据集可重复导入、可停止、可审计；
- 系统先以模块化单体交付，避免在数据量和业务尚未验证前引入过多分布式组件；
- 后续可平滑扩展至趋势 Connector、全文检索、向量检索和多人审核。
- V1 提供基于已发布词条的规则识别 API，不依赖向量服务或语义模型。

## 2. 架构决策

| 决策 | V1 选择 | 原因 |
|---|---|---|
| 主开发语言 | Java | 作为 V1 后端、领域模块和导入处理的统一实现语言。 |
| 应用框架 | Spring Boot 4.0.7 | 用于 Web/API、配置管理、依赖注入、事务和应用生命周期管理。 |
| 数据访问 | MyBatis Spring Boot Starter 4.0.1 | 显式维护领域 SQL 和事务边界，不使用 JPA；各领域通过 Mapper/持久化门面访问其拥有的数据。 |
| Java 运行时 | JDK 17.0.17 | 作为开发、构建和运行的统一 JDK 基线。 |
| 构建工具 | Apache Maven 3.9.11 | 统一依赖管理、模块构建、测试和打包流程。 |
| 管理页面 | 静态 HTML、CSS、原生 JavaScript ES Modules | 前后端通过 REST API 分离；不使用 Thymeleaf，不引入 Node.js 和前端打包工具。 |
| 前端交付 | Spring Boot 标准静态资源目录 | 页面源码直接位于 `src/main/resources/static/`，由 Maven 随后端资源一并打入 JAR。 |
| 服务形态 | 按微服务边界组织的模块化单体（Modular Monolith） | V1 不承担微服务部署与分布式一致性成本，但每个领域独立拥有模型、数据访问和事件契约，可在需要时拆分。 |
| 运行形态 | 单个 Web/API 应用进程 | V1.0 支持 CHIME、Buzzword 手工导入，由受控管理操作同步执行；暂无独立 Worker。 |
| 权威数据源 | MySQL 8.0 业务表 | 与既有数据库设计一致；正式词条及其子表是运行时权威数据。 |
| 消息与缓存 | V1 暂不引入 MQ 或 Redis | 当前没有独立、耗时且需可靠排队的异步任务；后续按真实需求引入 RocketMQ 作为领域异步协作、Redis 作为缓存等辅助能力。 |
| 身份标识 | V1 使用固定操作者标识 | 不建设登录和权限系统；通过 `X-Actor-Id` 与配置白名单提供开发期操作者标识，并以 `CurrentActorProvider` 隔离未来 IDSAAS 接入。V1 仅运行在本地或可信内网。 |
| 搜索 | MySQL 基础查询优先 | V1 数据规模可控；OpenSearch/向量检索在明确性能或召回需求后再引入。 |
| 原始材料 | 默认不持久化 | 只留最小化的候选、摘要、链接与审计信息；确需复核时短期受限暂存。 |
| 采集模式 | 多来源手工数据集导入 | 通用编排服务统一治理，每个来源使用独立 Importer；自动采集和趋势 Connector 后置。 |

## 3. 系统上下文

```text
编辑 / 审核人员 ──管理后台/API──┐
                                │
业务使用方 ─────查询 API────────┼── VibeLex 应用服务 ── MySQL
                                │
CHIME 手工导入 ──────────────────┘
```

外部数据来源不直接写入 MySQL 的正式词条表；所有输入均通过导入或采集模块落入候选域，再由审核流程进入正式知识库。

## 4. 容器与部署结构

```text
                    ┌─────────────────────────────┐
                    │          管理后台            │
                    │ 编辑、审核、来源与任务管理   │
                    └──────────────┬──────────────┘
                                   HTTPS
                    ┌──────────────▼──────────────┐
                    │       VibeLex Web/API        │
                    │ 词条、审核、查询、导入与平台接入 │
                    └──────────────┬──────────────┘
                                   SQL
                    ┌──────────────▼──────────────┐
                    │           MySQL 8            │
                    └─────────────────────────────┘
```

V1 将管理后台与 Web/API 部署为同一个应用，并在路由和资源访问上隔离。CHIME 导入通过受控管理接口同步分批执行；若真实导入耗时已影响操作体验，再拆出 Worker 并引入消息中间件。

## 5. 领域边界与模块所有权

V1 以未来可独立部署的微服务边界组织代码和数据所有权，但先以一个 Web/API 进程部署。领域之间通过应用服务命令或只读查询契约协作；禁止跨领域直接读写对方的持久化模型。领域事件契约保留为后续扩展，不作为 V1 的运行时基础设施。

```text
来源治理与导入域 ── CandidateDiscovered ──► 候选发现域
                                              │ ReviewRequested
                                              ▼
                                           简单审核域
                                              │ ReviewApproved / Returned
                                              ▼
                                          语言知识域
                                      ┌───────┴────────┐
                                      ▼                ▼
                                   查询域           识别域
```

| 领域模块 | 拥有的业务能力与数据 | 对外提供 | 不负责 |
|---|---|---|---|
| 操作者上下文适配层 | 固定用户白名单、`X-Actor-Id` 解析和 `CurrentActorProvider` | 当前操作者字符串标识 | 登录、密码、角色和权限系统 |
| 来源治理与导入域 | `source_import_runs`、Importer 注册表、通用编排、来源字段映射和运行日志 | 通过许可证门禁的 CHIME、Buzzword 手工导入 | 自动采集、词义判断和正式发布 |
| 候选发现域 | `candidate_entries`、人工录入、归一化、来源内去重、重复提示、编辑和审核状态 | 可编辑候选、审核中锁定状态及导入追溯信息 | 正式词条写入和复杂审核工作流 |
| 简单审核域 | 候选提交、分页审核、详情查看、批量批准、批量退回和发布编排 | 基于 `candidate_entries` 的单级审核能力 | 审核草稿、任务领取、多人审核、双人复核和工作流引擎 |
| 语言知识域 | `meme_entries`、义项、变体、例句、规则、风险策略、`meme_evidence`、`meme_revisions` | 正式发布、归档、回滚以及已发布知识事件 | 候选编辑、采集任务、候选去重和审核任务分配 |
| 查询域 | 已发布词条的读模型、查询 API、结果展示策略 | 词条、义项、变体和证据摘要查询 | 修改正式词条、处理候选或审核 |
| 识别域 | 已发布词条派生的召回索引、匹配规则、消歧与解释 | 文本识别 API | 修改词条事实或绕过发布流程 |

来源治理与导入域只能产生候选；语言知识域是唯一可写入正式词条和证据的领域；查询域和识别域仅消费已发布知识。

### 5.1 后续跨领域事件契约

本节定义未来引入独立 Worker、消息中间件或拆分服务时使用的事件边界。V1 不发布、不消费这些异步事件；当前跨领域操作由同步应用服务编排完成。事件结构、版本和幂等键须稳定，以便未来改由 RocketMQ 或事件总线传递。

| 事件 | 发布者 | 消费者 | 含义 |
|---|---|---|---|
| `DatasetImported` | 来源治理与导入域 | 候选发现域、审计 | 一个数据集版本已通过文件与来源校验并完成解析。 |
| `CandidateDiscovered` | 来源治理与导入域 | 候选发现域 | 发现一条最小化、可追溯的候选记录。 |
| `ReviewRequested` | 候选发现域 | 审核工作流域 | 候选从 `editing` 或 `returned` 进入 `pending_review` 并锁定编辑。 |
| `ReviewApproved` | 审核工作流域 | 语言知识域 | 候选审核批准，事务性发布正式词条并生成正式版本。 |
| `ReviewReturned` | 审核工作流域 | 候选发现域 | 候选审核退回并附带原因，状态变为 `returned`，允许修改后重新提交。 |
| `EntryPublished` | 语言知识域 | 查询域、识别域、审核工作流域 | 正式词条首次发布，可构建或更新派生读模型。 |
| `EntryChanged` | 语言知识域 | 查询域、识别域、审计 | 已发布词条、义项、变体、规则或风险策略发生变化。 |
| `SourceDisabled` | 来源治理与导入域 | 候选发现域、审核工作流域、语言知识域 | 来源停用，停止任务并标记相关候选/证据进入复核范围。 |
| `EvidenceRecheckRequested` | 语言知识域或审核工作流域 | 审核工作流域 | 来源失效、争议或规则变化需要重新核验词条结论。 |

事件载荷只传递对象 ID、来源/版本 ID、发生时间、操作者外部标识和必要业务原因，不携带大段原始内容。消费者必须依赖事件 ID 或业务幂等键去重。

### 5.2 微服务就绪的工程骨架

代码仓库按领域模块组织；每个领域内部采用 `api`、`application`、`domain`、`infrastructure` 四层。即使 V1 共用一个 MySQL 实例，也应按领域隔离迁移、仓储和写入入口。

```text
pom.xml                             唯一 Maven 构建入口
src/main/java/                      Web/API 与领域代码
  .../actorcontext/                 CurrentActorProvider
  .../sourceingestion/              数据文件导入运行与 Importer
  .../candidatediscovery/           候选、归一化和去重
  .../reviewworkflow/               候选单级审核与正式发布编排
  .../lexicon/                      词条、义项、证据、风险和版本
  .../query/                        正式知识查询 API
  .../recognition/                  规则召回、打分和消歧
src/main/resources/
  application.yml
  db/migration/                     Flyway 数据库迁移
  static/                           Spring Boot 静态管理页面
    index.html
    assets/
      css/                          页面样式
      js/                           页面逻辑与 REST API 调用
src/test/java/                      单元、集成与契约测试

data/                               操作者手工放置的 CHIME、Buzzword 文件
```

构建基线固定为 JDK 17.0.17、Spring Boot 4.0.7 和 Maven 3.9.11。项目根目录 `pom.xml` 是唯一 Maven 构建入口。前端使用 HTML、CSS 和原生 JavaScript ES Modules，不引入 Node.js、npm、pnpm 或前端打包工具。静态源码直接位于 `src/main/resources/static/`，由 Spring Boot 标准资源处理流程打入同一个 JAR。

`src/main/resources/static/` 只承载静态页面资源，不放置后端配置或业务数据。页面根据词条、候选、审核、导入和识别等实际功能拆分，并优先复用通用请求与页面组件。

`shared/` 不得承载业务规则或共享领域实体；它只包含技术能力与稳定契约。一个领域若要读取另一个领域的数据，应调用其应用服务或订阅其事件，不得引用对方的 repository 或 ORM model。

## 6. 数据域与权威边界

```text
来源治理与导入域              候选发现域 / 简单审核域
source_import_runs          candidate_entries

语言知识域                   查询域 / 识别域（派生）
meme_entries                发布词条读模型、搜索索引、识别索引
meme_senses                 V1 在同一进程内同步刷新或定时重建
meme_variants
meme_examples
meme_evidence
meme_revisions
```

| 数据域 | 写入者 | 是否可公开查询 | 保留原则 |
|---|---|---|---|
| 来源治理与导入域 | 来源治理与导入域 | 否，仅管理入口可访问 | 保存治理、运行和最小化审计元数据 |
| 候选发现域 | 候选发现域 | 否 | 保存人工或导入候选、来源追溯与直接审核状态；候选池不维护版本快照 |
| 简单审核域 | 审核应用服务 | 否 | 直接更新 `candidate_entries` 审核状态；批准时事务性写入正式词条及版本 |
| 语言知识域 | 语言知识域 | 是，按风险策略控制 | 作为业务权威数据长期维护 |
| 查询/识别派生域（后续） | 查询域、识别域 | 是，仅提供已发布内容的派生结果 | 后续按已发布知识构建，不作为事实权威源 |
| 暂存域（可选） | 导入应用服务 | 否，仅受限人员 | 默认不保存；保存时必须有过期时间 |

`meme_evidence` 是正式词条结论的证据表，不是所有导入记录的垃圾桶。只有审核确认的候选材料才能被转换或引用为证据。

## 7. 核心数据流

### 7.1 数据集导入（V1 首要路径）

```text
操作者从项目 data/ 目录选择 CHIME 文件
  ↓
创建导入运行记录并上传文件
  ↓
导入应用服务写入默认版本与权利核验信息，并校验文件哈希、格式和必要字段
  ↓
来源专属 Importer 映射为标准候选记录
  ↓
预处理：清洗 → 归一化 → 去重 → 风险提示
  ↓
candidate_entries（editing，可编辑） + source_import_runs（导入运行）
  ↓
编辑补充词条、释义等信息并直接提交，候选变为 pending_review 并锁定
  ↓
审核批准后在同一事务中写入 meme_entries 及其子表、生成 meme_revisions，并将候选标记为 published；退回后候选变为 returned，可修改后重新提交
```

V1.0 实现 `CandidateImporter` 统一契约以及 CHIME、Buzzword 导入器。后续来源可复用许可证门禁、文件指纹、运行记录、归一化和候选持久化，并独立维护格式解析、字段映射和来源质量规则。

### 7.2 编辑手工录入

```text
编辑人工创建 candidate_entries 候选
  ↓
填写词形、义项、语境、风险和来源证据建议
  ↓
归一化与重复校验
  ↓
直接提交后候选锁定；简单审核批准时由语言知识域在事务中发布并创建正式版本，退回后允许继续编辑
```

### 7.3 受控趋势采集（V1 后续）

```text
调度器检查来源与任务门禁
  ↓
Connector 在白名单端点内低频获取聚合趋势信号
  ↓
生成 candidate_trend_signals / 候选复核任务
  ↓
编辑核验后影响词条热度或新增候选
```

趋势信号不是自动发布依据，也不应默认保存来源中的完整原始内容。

## 8. 导入与预处理流水线

预处理是导入/采集模块内部的应用服务，不属于正式词条模块。建议按以下固定阶段实现：

1. **获取与校验**：从项目 `data/` 目录读取 CHIME 文件；版本未提供时使用 `manual-local`，权利核验默认 `approved/system`，同时计算实际文件哈希。
2. **格式解析**：按 Importer 读取 JSON、CSV、Parquet 或其他允许格式，拒绝异常文件、超大文件或未知字段。
3. **字段映射**：映射为统一候选 DTO，例如 `term_raw`、`definition_raw`、`source_url`、`observed_at`、`source_record_key`。
4. **最小化处理**：截断不必要长文本，剔除未允许字段和个人信息。
5. **归一化**：依照 [normalization.md](../../reference/normalization.md) 生成规范词形。
6. **去重与聚类**：先按来源内键幂等去重，再按规范词形、语言和相似度关联已有候选或正式词条。
7. **质量与风险提示**：检测空释义、异常长度、敏感内容、低置信度或语言不匹配；产生提示，不替代人工结论。
8. **候选持久化**：写入候选池与运行统计；无法处理的记录保存错误原因和最小诊断信息。

## 9. API 与后台边界

V1 建议提供 REST 风格 API；具体路径可在实现阶段确定，但资源边界应稳定。V1 不实现登录、角色和权限系统，通过固定操作者白名单与 `X-Actor-Id` 提供操作者标识，所有业务代码统一从 `CurrentActorProvider` 读取当前操作者。

| API 域 | 典型调用方 | 典型能力 |
|---|---|---|
| 公开/业务查询 | 应用客户端 | 查询已发布词条、变体、义项和受控的识别结果 |
| 编辑工作台 | 固定操作者 | 人工创建候选、编辑候选、查看详情、分页筛选和批量提交审核 |
| 来源与导入管理 | 固定操作者 | 填写 CHIME 权利核验信息、上传文件、触发导入、查看运行日志 |
| 候选审核 | 固定操作者 | 分页查看待审候选、查看详情、批量批准和批量退回 |
| 正式词条管理 | 固定操作者 | 分页查询正式词条、查看 ID、释义和详情 |
| 保留的正式词条变更接口 | 固定操作者 | 提供 `entry_change_sets` 的历史兼容后端能力；当前候选页面与候选审核流程不调用 |

固定操作者示例为 `editor01`、`reviewer01`、`admin01` 和 `system`。所有 `created_by`、`submitted_by`、`reviewed_by`、`changed_by`、`initiated_by` 等字段统一使用 `VARCHAR(128)`。该机制只提供开发期操作标识，不构成生产级身份认证。

V1 允许同一操作者提交并审核自己的候选。系统记录 `submitted_by` 和 `reviewed_by`，暂不校验两者是否相同。

## 10. V1 导入运行模型

| 操作 | 执行方式 | 幂等键 | 失败策略 |
|---|---|---|---|
| CHIME 导入 | 管理接口手动触发，同步分批执行 | `import_fingerprint + attempt_no` | 已成功或部分成功的相同指纹直接返回原运行；失败或取消后允许递增 attempt_no 重试 |
| 预处理 | 同一导入请求内按批处理 | 导入运行 + 记录键 + 处理版本 | 单条失败隔离，整体标记部分成功 |

每次导入都必须写 `source_import_runs`（或等价运行表），包括发起者、来源、文件版本/哈希、开始结束时间、统计数据和错误摘要。V1 不引入任务队列、后台 Worker、自动重试、定时扫描或自动补偿。

---

## 11. 一致性、审计与可恢复性

- 候选提交、审核批准发布和正式词条回滚等跨多表业务操作应使用 MySQL 事务。
- `meme_entries` 及其子表只保存当前生效数据；未审核内容直接保存在 `candidate_entries`，不创建候选草稿或审核草稿。
- `pending_review` 候选禁止编辑；退回为 `returned` 后允许修改并重新提交。
- 同一来源、数据版本与文件哈希的重复导入必须幂等；已完成运行直接返回原结果，失败或取消运行允许递增 attempt_no 重试，候选按指纹和来源记录键去重。
- 正式词条每次重要变更生成 `meme_revisions` 快照；候选处理保留来源、运行、解析器和处理版本。
- 正式词条禁止硬删除，只能转为 `disabled` 或 `archived`；候选可按明确的数据清理策略处理。
- CHIME 权利核验状态改为 `rejected` 或 `expired` 后，系统应停止新的导入请求；历史运行与候选继续保留用于追溯。
- 数据库执行常规备份与恢复演练；短期暂存材料不应成为恢复正式词条的唯一依据。

---

## 12. 安全与合规边界

- V1 不保存账号密码，也不实现登录、角色分配或权限配置；固定操作者仅用于本地或可信内网环境。
- `X-Actor-Id` 必须属于配置白名单，并通过 `CurrentActorProvider` 提供给业务代码；该标识不作为强安全审计证据。
- Web/API 与数据库使用最小权限账户；导入应用服务只读取获批准的数据文件位置。
- API 凭据使用受控密钥存储，通过引用注入任务；禁止出现在代码库、任务参数和普通日志中。
- 导入文件必须限制类型、大小、压缩层数和解析资源，防止恶意文件和资源耗尽。
- 不实现绕过 robots、验证码、登录墙、反爬或服务条款限制的逻辑。

## 13. 可扩展路径

| 触发条件 | 后续演进 |
|---|---|
| 需要生产级登录与权限控制 | 将 `CurrentActorProvider` 替换为 IDSAAS 适配实现，在 IDSAAS 中登记查询、编辑、审核和导入资源；数据库操作者字段保持不变。 |
| 识别 API 需要对外开放或区分调用方 | 区分公共识别与内部调试接口，按身份和使用场景控制未发布候选识别及策略字段的执行与返回。 |
| 导入耗时影响操作体验，或来源与任务显著增加 | 拆出 Worker，并引入 RocketMQ 承担导入任务和领域异步协作；保持候选 API 契约不变。 |
| 单级审核不再满足需要 | 引入 `meme_review_tasks`、任务领取、多人审核、禁止自审、双人复核和质量抽检。 |
| 接入多个外部来源 | 引入 `data_sources`、`source_collection_tasks`、来源停用和影响范围复核能力。 |
| 词条和查询量增长 | 引入 OpenSearch/Elasticsearch 作为派生索引，MySQL 继续为权威数据源。 |
| 语义召回需要提升 | 增加向量索引/向量数据库，按已发布义项构建可重建的派生向量。 |
| 多租户或行业词包 | 增加租户与权限边界，在候选、词条、审核和检索层一致隔离。 |
| 多模态数据验证有效 | 在独立受限管线中处理 MOD 等数据；不改变文本词条主库的最小化原则。 |

## 14. 实施顺序

### Milestone 1：正式词条与候选审核骨架

实现固定操作者上下文、候选直接提交与审核、词条/义项/变体/证据/版本的基础能力。候选是唯一可编辑对象，正式数据库表只保存已批准的生效内容。

### Milestone 2：候选池与预处理服务

实现 `candidate_entries`、人工录入、归一化、与已发布词条的重复提示、候选编辑、提交锁定、审核退回后重编以及直接发布。这是数据集导入和人工录入的共同落点。

### Milestone 3：数据文件导入器

实现 `data/` 目录文件选择、来源选择、版本与权利核验信息、文件哈希记录、Importer 注册表、CHIME 与 Buzzword JSON 字段映射及运行日志。操作者可覆盖版本和核验说明。

### Milestone 4：V1 闭环验证

用真实 CHIME 文件完成一次端到端导入、候选审核和词条发布验证，并使用已发布词条完成基础规则识别 API 验证；记录导入耗时、错误类型、重复率、审核采纳率和识别评测结果。

### 后续扩展（不属于 V1）

根据 V1 验证结果，评估其他数据集 Importer、自动采集 Connector、Worker、RocketMQ、Redis 缓存、趋势采集和搜索索引；它们均不作为 V1 前置条件。

## 15. V1 验收条件

1. 编辑可以人工创建或修改 `editing`、`returned` 候选，查看详情并单条或批量提交审核；
2. 候选提交后变为 `pending_review` 并禁止编辑；审核员可单条或批量批准、退回，退回后允许修改并重新提交；
3. 至少可导入一个授权数据集（优先 CHIME），每条候选可追溯到数据版本、运行和来源；
4. 重复执行同一数据版本导入会返回已有完成运行或创建受控重试，不会重复创建候选；
5. 导入失败可定位到具体运行和记录，且不影响已发布词条；
6. CHIME 导入默认使用 `approved/system` 权利核验信息；状态被改为 `rejected` 或 `expired` 时无法执行导入；
7. 不保存未经允许的大规模原始内容；
8. 审核批准后直接创建或更新正式词条并生成 `meme_revisions`，候选审核不创建或使用 `entry_change_sets`；
9. 正式词条列表支持分页和详情查看，并展示词条 ID 与候选释义对应的正式义项内容；
10. 业务客户端默认只查询 `published` 状态的正式词条数据；
11. 基础规则识别 API 能完成变体召回、上下文打分、义项消歧和冲突处理，不依赖向量服务；
12. 正式词条不存在硬删除入口，停用和历史保留分别使用 `disabled` 与 `archived`。
