# VibeLex V3.1：热梗百科爬取与 AI 信息提取设计

**产品版本：** V3.1

**状态：** 待评审

**新增来源：** 热梗百科（`https://regengbaike.com/`）

**文档日期：** 2026-07-30

---

## 1. 目标

V3.1 在 V3.0 多来源爬取框架上增加热梗百科，并使用一个不具备联网搜索能力的 OpenAI 兼容模型，对热梗百科页面中的已有信息进行提取、压缩和分类，并按词条释义整理例句。

```text
热梗百科 sitemap
        ↓
枚举新词条页面
        ↓
抓取标题、摘要、正文、分类和发布时间
        ↓
普通 OpenAI 兼容模型
        ↓
提取简短释义、来源背景、已有例句和系统分类
        ↓
服务端严格校验
        ↓
判重并进入候选词条池
```

V3.1 沿用 V3.0 的统一同步语义：

```text
检查点为空    枚举该来源全部词条
检查点存在    只枚举检查点之后的新词条
```

### 1.1 现有基础

V3.0 已提供：

- `CrawlConnector` 多来源扩展接口；
- 无检查点完整枚举、有检查点增量枚举的统一同步流程；
- `crawl_checkpoints` 来源检查点；
- `crawl_records` URL 级队列、终态和失败重试；
- 正式词条、正式变体和候选词条统一判重；
- 候选创建、审核发布以及按来源查询的管理页面；
- 基于 Responses API 和 `web_search` 的 AI 词形变体生成能力。

### 1.2 V3.1 建设内容

- 新增热梗百科 Connector；
- 支持网页手动爬取和定时爬取；
- 使用最大词条数字 ID 作为增量检查点；
- 抓取并保存页面原始结构化材料；
- 新增普通 OpenAI `/chat/completions` 兼容客户端；
- 保留现有 Responses API 联网变体生成能力；
- AI 事实字段仅整理热梗百科已有信息，例句允许按页面语境或释义生成，不调用联网搜索；
- AI 提取简短释义、来源背景、已有例句和系统分类；
- 服务端校验 AI 输出，要求有效词条包含 3 条去重例句并拒绝非法分类；
- 复用 V3.0 判重、候选创建、任务取消、重试和检查点推进机制；
- 在爬取记录和候选中保留模型、提示词及处理版本信息。

## 2. 来源技术基线

2026-07-30 的只读样本结果：

| 项目 | 结果 |
|---|---|
| 首页 | `https://regengbaike.com/` |
| sitemap | `https://regengbaike.com/addons/cms/sitemap/archives/sitemap.xml` |
| sitemap 规模 | 约 2,240 个详情 URL，以运行时实际结果为准 |
| 详情 URL | `https://regengbaike.com/{numericId}.html` |
| 已观察 ID 范围 | 1 至 2251，中间允许缺号 |
| 词条名称 | 页面 `h1` |
| 页面摘要 | `meta[name=description]` |
| 正文 | `.article-text` |
| 发布时间 | `time[datetime]` |
| 来源分类 | 面包屑分类 |
| 规范链接 | canonical URL |
| sitemap `lastmod` | 未提供 |
| HTTP `ETag` / `Last-Modified` | 未发现可依赖的稳定值 |

热梗百科页面摘要和正文只作为 AI 的原始输入，不直接写入候选释义。抽样中存在以下内容质量特征：

- 释义、出处、传播事件和人物介绍混在同一段；
- 页面摘要通常仍有 50～160 字，部分正文超过 500 字；
- 部分记录更接近人物或普通名词百科，不一定是网络梗；
- 页面可能没有明确使用例句；
- 个别内容存在重复、语病或前后不一致。

因此，热梗百科在 V3.1 中定位为“候选词条发现与原始材料来源”，候选字段由 AI 在页面已有内容范围内整理。

## 3. 来源标识与字段映射

```text
source_code       regengbaike
source_name       热梗百科
parser_version    regengbaike-html-v1
processor_version regengbaike-ai-extraction-v2
```

Connector 原始字段映射：

| 页面字段 | 原始抓取字段 |
|---|---|
| 数字词条 ID | `sourceRecordKey` |
| canonical URL | `sourceUrl` |
| `h1` | `term` |
| `meta description` | `sourceSummary` |
| `.article-text` 清理后的文本 | `sourceBody` |
| 面包屑分类 | `sourceCategory` |
| `time[datetime]` | `sourcePublishedAt` |
| 页面抓取时间 | `fetchedAt` |

HTML 使用以下确定性规则清理：

- 删除脚本、样式、导航、推荐卡片和 HTML 标签；
- 解码 HTML 实体；
- 合并连续空白；
- 保留正文标点和段落边界；
- Connector 输出原始材料，释义整理和分类由后续内容处理器完成。

## 4. 检查点设计

热梗百科使用详情页数字 ID 作为单调递增游标：

```json
{
  "maximumArchiveId": 2251
}
```

### 4.1 首次爬取

检查点为空时：

1. 下载 sitemap；
2. 解析所有符合 `/{numericId}.html` 的同站详情 URL；
3. 按数字 ID 升序排列；
4. 为尚未存在于 `crawl_records` 的记录创建待处理任务；
5. 将 sitemap 中的最大数字 ID 写入 `pending_checkpoint`；
6. 全部记录处理完成且没有失败后提交检查点。

### 4.2 增量爬取

检查点存在时：

```text
archiveId > checkpoint.maximumArchiveId
```

只有满足该条件且尚未存在于 `crawl_records` 的 URL 才进入处理队列。ID 中间缺号不视为异常。

### 4.3 没有新内容

- sitemap 最大 ID 与检查点相同：返回 `no_change`；
- 页面提示“未发现新内容，检查点保持不变”；
- 不创建空任务记录；
- 不重复抓取已有详情页。

### 4.4 检查点处理边界

该来源没有可依赖的页面修改时间，因此检查点按以下边界运行：

- 旧 ID 页面后续修改不会被自动重新处理；
- 已处理 URL 保持 V3.0 永久终态；
- 日常同步始终按数字 ID 向前推进，旧页面处理记录不参与增量枚举。

## 5. LLM 架构调整

当前 `AiVariantGenerator` 同时承担业务逻辑、Responses API 请求、`web_search` 工具调用、搜索次数校验和引用提取，无法直接用于普通 OpenAI 兼容模型。

V3.1 将模型通信与业务场景拆分：

```text
业务场景
├── AiVariantGenerator
│     └── ResponsesWebSearchLlmClient
│           └── /responses + web_search
│
└── RegengBaikeAiExtractor
      └── OpenAiChatCompletionsClient
            └── /chat/completions，无 tools
```

### 5.1 通用客户端契约

```java
public interface LlmClient {
  String complete(LlmRequest request);
}

public record LlmRequest(
    String model,
    String systemPrompt,
    String userContent,
    BigDecimal temperature,
    int requestTimeoutSeconds) {}
```

模型客户端只负责：

- 构造协议请求；
- 发送 HTTP 请求；
- 处理认证、超时和非 2xx 响应；
- 从供应商响应中提取模型文本；
- 不理解词条、释义、分类、例句或候选业务。

### 5.2 两种协议客户端

`ResponsesWebSearchLlmClient`：

- 承接现有 `/responses` 调用；
- 保留 `web_search` 工具；
- 保留搜索次数和结构化引用校验；
- 现有 AI 变体行为保持不变。

`OpenAiChatCompletionsClient`：

- 调用 `POST {base-url}/chat/completions`；
- 使用 `system` 和 `user` 两条 message；
- 不发送 `tools`、`tool_choice` 或任何搜索参数；
- 从 `choices[0].message.content` 读取结果；
- 兼容返回 JSON 字符串的常规模型服务。

第一版通过提示词要求模型只输出 JSON，并由服务端严格解析，以兼容未实现 `response_format` 的 OpenAI 兼容服务。

### 5.3 供应商与场景配置分离

```yaml
vibelex:
  llm:
    providers:
      ark-search:
        protocol: responses
        base-url: ${VIBELEX_SEARCH_LLM_BASE_URL}
        api-key: ${VIBELEX_SEARCH_LLM_API_KEY}
        model: ${VIBELEX_SEARCH_LLM_MODEL}
        request-timeout-seconds: ${VIBELEX_SEARCH_LLM_REQUEST_TIMEOUT_SECONDS:180}

      general-openai:
        protocol: chat-completions
        base-url: ${VIBELEX_GENERAL_LLM_BASE_URL}
        api-key: ${VIBELEX_GENERAL_LLM_API_KEY}
        model: ${VIBELEX_GENERAL_LLM_MODEL}
        request-timeout-seconds: 90

    scenarios:
      variant-generation:
        enabled: false
        provider: ark-search
        prompt: classpath:prompts/variant-generation.md
        temperature: 0.2
        web-search-enabled: true
        web-search-max-keyword: 2

      regengbaike-extraction:
        enabled: true
        provider: general-openai
        prompt: classpath:prompts/regengbaike-extraction.md
        temperature: 0.1
        maximum-source-characters: 12000
        minimum-confidence: 0.6
```

启动热梗百科任务前必须执行配置预检。来源、AI 场景、供应商、模型、地址或提示词缺失时，任务在规划阶段直接失败，不得先创建数千条待处理记录。

联网 Pro 模型的完整响应时间可能超过 Lite 模型。搜索 provider 默认超时为 180 秒，可通过 `VIBELEX_SEARCH_LLM_REQUEST_TIMEOUT_SECONDS` 调整；爬虫和文件导入 Worker 默认租约为 240 秒，必须始终高于模型请求超时，避免慢请求仍在执行时记录被其他 Worker 回收。

## 6. 爬取处理流水线

V3.0 的 `CrawlConnector.fetch()` 直接返回可入候选的 `CrawledEntry`。V3.1 增加原始抓取结果和内容处理器，以避免把 AI 调用写进具体 Connector。

```java
public record FetchedCrawlEntry(
    String term,
    String sourceSummary,
    String sourceBody,
    List<String> sourceExamples,
    String sourceCategory,
    List<String> sourceTags,
    String sourceUrl,
    String sourceRecordKey,
    Instant sourcePublishedAt,
    String parserVersion) {}

public interface CrawlEntryProcessor {
  boolean supports(String sourceCode);

  CrawledEntry process(FetchedCrawlEntry source);
}
```

处理器注册表按 `sourceCode` 选择处理器：

```text
popcidian
  └── PopCidianAiEnricher
        保留波普释义、分类和全部原始例句，联网补充起源证据并在不足时补足到至少 3 条

regengbaike
  └── RegengBaikeAiExtractor
        使用普通 OpenAI 兼容模型提取信息
```

Worker 流程调整为：

```text
领取 crawl_record
        ↓
Connector.fetch 抓取确定性原始材料
        ↓
保存原始材料
        ↓
CrawlEntryProcessor.process
        ↓
服务端校验处理结果
        ↓
CandidateService.createFromCrawler
        ↓
candidate + crawl_record 终态同一事务提交
```

网页请求和 AI 请求均位于候选数据库事务之外，避免长时间占用事务和连接。

## 7. 原始材料与 AI 结果留存

为避免模型失败后重复抓网页，并支持排查和重新处理，V3.1 扩展 `crawl_records`：

```sql
ALTER TABLE crawl_records
  ADD COLUMN source_payload MEDIUMTEXT NULL COMMENT '确定性抓取的原始结构化材料 JSON',
  ADD COLUMN processor_version VARCHAR(64) NULL COMMENT '内容处理器版本',
  ADD COLUMN ai_model VARCHAR(255) NULL COMMENT '实际使用的模型名称',
  ADD COLUMN ai_output MEDIUMTEXT NULL COMMENT '通过校验的 AI 结构化输出 JSON',
  ADD COLUMN fetched_at DATETIME(3) NULL,
  ADD COLUMN ai_processed_at DATETIME(3) NULL;
```

`source_payload` 保存结构化文本，不保存完整 HTML：

```json
{
  "term": "尊嘟假嘟",
  "sourceSummary": "页面原始摘要",
  "sourceBody": "清理标签后的正文",
  "sourceCategory": "网络流行语",
  "sourcePublishedAt": "2023-08-01T10:00:00Z",
  "sourceUrl": "https://regengbaike.com/1500.html"
}
```

重试时：

- `source_payload` 已存在：跳过网页请求，直接重新执行内容处理；
- `ai_output` 已存在且处理器版本未变化：跳过模型请求，继续候选判重和创建；
- 处理器版本变化：允许明确的重新处理操作清除旧 `ai_output`，日常增量任务不自动重做终态记录。

## 8. AI 输入规则

模型输入只使用当前热梗百科页面的材料：

```json
{
  "term": "词条名称",
  "source_summary": "页面摘要",
  "source_body": "清理后的正文",
  "source_category": "来源分类",
  "source_published_at": "来源发布时间"
}
```

输入限制：

- 不传入搜索工具；
- 不要求模型使用自身记忆补充事实；
- 不提供其他网站内容；
- 原始材料总长度默认不超过 12,000 个字符；
- 超长内容保留标题、摘要和正文前部，并在输入中标记发生截断；
- 提示词明确要求无法判断时返回待复核信息，不得自行补全。

提示词文件：

```text
classpath:prompts/regengbaike-extraction.md
```

## 9. AI 输出契约

模型只允许输出一个 JSON 对象：

```json
{
  "is_valid_meme": true,
  "definition": "“真的假的”的谐音表达，通常用于以卖萌语气表示惊讶或确认。",
  "origin": "原文称该表达出自相关网络账号发布的文案。",
  "examples": [
    "尊嘟假嘟？"
  ],
  "category": "homophone",
  "confidence": 0.88,
  "needs_review": false,
  "issues": []
}
```

字段含义：

| 字段 | 必填 | 说明 |
|---|---:|---|
| `is_valid_meme` | 是 | 是否适合作为网络梗或网络流行语候选 |
| `definition` | 条件必填 | 只解释含义和典型使用方式 |
| `origin` | 否 | 原文已有的出处、人物、事件或传播背景 |
| `examples` | 是 | 有效词条固定 3 条完整例句；优先提取原文，没有现成例句时按语境或释义生成 |
| `category` | 是 | VibeLex 固定分类代码 |
| `confidence` | 是 | 0～1 的处理置信度 |
| `needs_review` | 是 | 是否存在歧义、矛盾、截断或信息不足 |
| `issues` | 是 | 简短问题代码或说明数组 |

### 9.1 释义规则

- 目标长度 30～100 个汉字，最多两句话；
- 只回答“是什么意思”和“通常如何使用”；
- 不混入长篇人物介绍、赛事过程或传播故事；
- 出处和传播过程进入 `origin`；
- 不添加原始材料中没有的具体事实；
- 不使用“据我所知”“可能是”等模型口吻。

### 9.2 来源背景规则

- 只提取原文明确提到的来源、人物、事件和传播过程；
- 原文没有可靠来源时返回空字符串；
- 原文互相矛盾时保留简短描述并设置 `needs_review=true`；
- 不把来源背景再次重复到 `definition`。

### 9.3 例句规则

- `is_valid_meme=true` 时固定返回 3 条互不重复的例句；
- 每条必须完整、自然、可独立理解，脱离上下文仍能看出词条如何使用；
- 优先提取原文中可直接使用的例句；不足 3 条时先基于原文语境生成，再基于释义生成；
- 生成内容必须符合释义，不得引入原文没有的具体人物、平台、时间、地点、事件或来源事实；
- 不把人物介绍、新闻叙述、标题、来源故事、歌词或孤立短语直接当作例句；
- `is_valid_meme=false` 时返回 `[]`；
- 单条例句不得超过 2,000 个字符。

### 9.4 分类规则

模型只能返回现有固定分类：

```text
homophone
abbreviation
number_code
template_phrase
slang
emotion_expression
sarcasm
foreign_term
fandom_term
game_term
acg_term
livestream_term
workplace_term
other
```

来源原始分类仍独立保存在 `processing_note.source_category`，不得让来源分类动态扩展 VibeLex 枚举。

## 10. 服务端输出校验

AI 输出不能直接进入候选池，必须经过确定性校验。

### 10.1 JSON 与字段校验

- 去除可选 Markdown 代码围栏后解析 JSON；
- 根节点必须是对象；
- 拒绝未知顶级字段；
- 校验布尔值、数组、分类和置信度类型；
- `is_valid_meme=true` 时释义不能为空；
- 非法分类统一拒绝，不静默映射为模型自造分类；
- 字段超长时拒绝本次结果，不直接静默截断核心释义。

### 10.2 例句结构校验

- `is_valid_meme=true` 时，去重后必须恰好包含 3 条非空字符串例句；
- `is_valid_meme=false` 时，例句必须为空数组；
- 单条例句超过长度上限时拒绝本次输出；
- 生成例句不要求在原文中逐字匹配，语义质量由提示词约束和人工抽样复核保证。

### 10.3 处理结果决策

| 条件 | 处理结果 |
|---|---|
| `is_valid_meme=false` | `crawl_record=ignored`，保存原因 |
| 有有效释义且 `confidence >= minimum-confidence` | 正常创建 `editing` 候选 |
| 有有效释义但低置信度或 `needs_review=true` | 创建 `editing` 候选，并标记 AI 待复核 |
| 无有效释义、JSON 非法或输出违反契约 | 按处理失败进入重试 |
| 达到最大尝试次数仍无法提取 | `crawl_record=failed`，允许后续人工重新启动重试 |

低置信度不新增候选状态，继续使用现有 `editing`，避免扩大审核状态机。候选页面通过处理说明展示“AI 提取结果待复核”。

## 11. 候选字段映射

| AI/来源字段 | 候选字段 |
|---|---|
| 页面 `term` | `candidate_entries.term_raw` |
| 归一化词名 | `candidate_entries.normalized_term` |
| AI `definition` | `candidate_entries.definition_raw` |
| 页面 canonical URL | `candidate_entries.source_url` |

| `crawler` | `candidate_entries.source_type` |
| Worker `actor-id` | `candidate_entries.created_by` |
| `editing` | `candidate_entries.status` |

`processing_note` 增加：

```json
{
  "source_code": "regengbaike",
  "source_name": "热梗百科",
  "source_record_key": "1500",
  "source_category": "网络流行语",
  "category": "homophone",
  "origin": "AI 从原文提取的来源背景",
```

## 12. 判重、事务与重试

### 12.1 判重

继续复用 V3.0 判重范围：

1. `meme_entries.normalized_term`；
2. 有效的 `meme_variants.normalized_variant`；
3. 任意状态的 `candidate_entries.normalized_term`。

AI 不允许修改页面词条名称，判重始终以 Connector 提取的 `h1` 为准。

### 12.2 事务边界

```text
网页请求                 无数据库事务
保存 source_payload      短事务
AI 请求                  无数据库事务
保存 ai_output           短事务
最终判重 + 创建候选
  + crawl_record 终态     同一事务
```

### 12.3 重试分类

| 失败类型 | 行为 |
|---|---|
| 网页超时或非 2xx | 使用 V3.0 阶梯退避重试 |
| HTML 关键字段缺失 | 重试后标记 `failed` |
| 模型超时或非 2xx | 保留 `source_payload`，只重试 AI |
| 模型 JSON 无法解析 | 保留原始错误摘要并重试 AI |
| AI 输出违反契约 | 按 AI 处理失败重试 |
| 页面不存在 | `ignored` |
| AI 判断不是网络梗 | `ignored` |

错误信息最长保留 2,000 字符，页面继续使用现有错误查看和复制交互。

### 12.4 取消任务

- 停止后不再领取新记录；
- 正在执行的网页或 AI HTTP 请求不强制中断；
- 在途处理返回后必须再次检查来源任务是否仍为 `running`；
- 已取消时不得创建候选，将记录恢复为 `pending`，供下次启动继续处理；
- 已保存的 `source_payload` 和合法 `ai_output` 可在下次复用。

## 18. 文件导入任务化改造（Buzzword / CHIME）

V3.1 同步将本地文件导入改造成与网站词条爬取一致的“任务 + 逐条记录 + Worker”模式，解决原有导入只有运行统计、无法查看单条词条状态的问题。

### 18.1 数据模型

保留 `source_import_runs` 作为一次文件导入任务的主记录，新增 `source_import_records` 保存任务中的每个来源词条。逐条记录通过 `candidate_id` 关联成功创建的候选；重复、忽略和失败记录也必须保留，不因没有候选而丢失。

逐条记录至少保存：原始序号、来源记录键、词条、归一化词形、处理状态、处理阶段、重试次数、租约、错误信息、候选 ID、重复目标、原始处理说明和 AI 输出追溯字段。

### 18.2 精简状态

导入任务在记录规划阶段使用内部状态 `planning`；完成所有逐条记录入队后才进入 `running`。`planning` 不对用户作为词条状态展示，超过 10 分钟仍未完成规划的任务标记为失败。逐条记录后台状态固定为：

```text
pending       等待处理
processing    Worker 正在处理
imported      已创建候选
duplicate     已存在，未创建候选
ignored       原始数据无效或内容不适合导入
failed        达到最大重试次数后仍失败
```

管理页面将 `pending` 和 `processing` 合并显示为“待处理”，用户可见状态为“待处理、已导入、已存在、已忽略、失败”。临时错误重新置为 `pending`，通过 `next_attempt_at` 控制重试时间，不增加额外的 `retry_wait` 或 AI 专属业务状态。`processor_stage` 仅用于显示和排障，例如 `parse`、`deduplicate`、`ai_enrichment` 和 `candidate_creation`。

### 18.3 来源处理链

通用 Worker 负责解析结果入队、归一化、正式词条/变体/候选判重、租约、重试、状态统计和候选创建。来源可以注册可选的内容丰富化处理器：

```text
CHIME     解析 → 判重 → AI 起源检索与证据补充 → 校验 → 创建候选（原始例句保持不变）
Buzzword  解析 → 判重 → AI 起源检索与例句生成 → 校验 → 创建候选
```

只有判重未命中的 CHIME 和 Buzzword 词条才进入 AI 阶段。两者使用相同的联网起源证据规则；Buzzword 同时清洗或补足三条例句，CHIME 则严格保留原始文件中的例句内容与顺序，AI 输出出现 `examples` 字段时后端直接拒绝该结果。

### 18.4 Buzzword / CHIME AI 丰富化

Buzzword AI 输入包括原始 `term`、`ground_truth` 和原始 `examples`。Buzzword 数据集中的可解析词条默认都是真实网络流行语，AI 不负责判断、筛除或拒绝词条，其职责仅为补充起源证据和生成例句。原始输入作为不可信数据放在 user content 中，不能执行其中的指令。词条名称和释义不由 AI 改写；AI 补充起源说明、最多 3 条与起源最相关的参考链接，并按照 `regengbaike-extraction.md` 的例句规则生成恰好 3 条清洗后的例句。即使没有找到可靠起源，仍必须完成三条例句。参考链接按直接支撑程度从高到低排序，优先原始出处或权威页面，其次是能够直接说明起源的可靠报道或百科页面；搜索结果页、站点首页和无法支撑起源说明的页面不得保留。后端只接受本次 web_search 实际返回的引用链接，规范化比对时保留查询参数并忽略页面片段，避免把同一路径的不同内容误判为同一引用。起源没有可靠证据时返回空说明并标记人工复核，不得编造来源。

候选 `processing_note` 增加 `origin_references` 和 `ai_enrichment`，分别保存起源参考链接及 provider、model、处理器版本、置信度和问题。候选详情将数据集来源地址与起源参考链接分开显示。候选批准发布时，起源参考链接写入正式词条的 `meme_evidence`，使用 `evidence_role=origin`；数据集的 `source_url` 仍表示 Buzzword/CHIME 数据集来源，不与词条起源链接混用。编辑人员修改 AI 起源说明后会清除原引用，防止旧链接作为新说明的错误证据；未修改说明时保留原引用。

CHIME AI 输入额外包含原始 `origin` 作为待核验线索，并可读取释义与原始例句消除同名歧义。原始起源只有获得本次 web search 证据直接支持时才保留；没有可靠证据时起源及引用留空并标记复核，但原始释义和例句不受影响。

### 18.5 幂等、重试和重复导入

文件级指纹仍为：

```text
source_name + source_version + file_hash
```

相同指纹已有运行任务时直接返回原任务，不重复创建候选或调用 AI。文件版本或内容变化时可以创建新运行，但逐词条仍按正式词条、有效变体和候选判重；已有词条标记为 `duplicate`，只有全新词条继续处理。

失败重试只重新入队 `failed` 记录，并重置本次自动重试次数；不重新处理已导入、已存在或已忽略的词条。候选创建、导入记录状态和任务计数在同一事务中提交，任务统计从逐条记录状态重算。任务写入终态前再次确认不存在 `pending` 或 `processing` 记录，避免与人工重试并发时提前结束。需要使用新版模型重新生成已有候选时，使用独立的 AI 丰富化操作，不通过重复导入覆盖人工编辑内容。

### 18.6 管理页面

导入页面包含两层：

1. 导入运行列表：显示来源、文件、运行状态、最近更新时间、总数、已导入、已存在、已忽略和失败数量；运行中任务支持软停止；
2. 运行详情词条列表：支持按词条搜索、按处理结果筛选、分页、查看处理详情、查看候选/重复目标和重试失败词条。

导入处理状态与候选治理状态分开显示。前者使用本节定义的五类用户可见状态，后者继续使用 `editing`、`pending_review`、`returned` 和 `published` 等候选生命周期状态。

### 18.7 文件导入验收标准

1. CHIME 和 Buzzword 都可以创建导入任务并查看逐词条记录；
2. CHIME 仅通过 AI 补充起源说明和最多 3 条参考链接，原始释义、例句内容及顺序保持不变；
3. CHIME 和 Buzzword 仅对判重未命中的词条调用 AI；
4. 每个可解析且判重未命中的 Buzzword 词条都生成 3 条符合例句规则的例句，不由 AI 判断词条是否属于网络流行语；
5. 起源说明和参考链接可以在词条详情中追溯；
6. 重复、忽略、失败词条均保留记录并显示原因；
7. 临时错误可自动重试，失败词条支持单条或批量重新入队；
8. 相同文件指纹重复导入保持幂等；
9. 文件导入任务列表和词条详情分页、筛选可用；
10. 导入状态与候选审核发布状态不混淆。
